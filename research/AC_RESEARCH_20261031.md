## 2. Track A exactness and system bottlenecks

A: 3.1M records, 238,836,234 input bytes, 72 UTC hours, 1,842 seed-dependent endpoint templates, 126,908 printed groups, 10,113,024 output bytes. Duplicate requests count twice; `status>=500` counts as an error, 499 does not; p50/p95/p99 are sorted nearest-rank elements, **not interpolated**. All 32-bit latencies including zero/max must be accepted. Input time order has **no guaranteed lateness bound**, so any early-finalization strategy must retain exact fallback. Bytewise endpoint sorting is exact, including prefixes and trailing path characters.

Current winning A source: 256 KiB block tasks, four interleaved parse streams/worker, ~12 workers on the scoring host, `mmap`, AVX2 space discovery and decimal conversion, worker-private 16K-entry endpoint dictionaries replicated from an append-only globally published list, exact six-byte `(u32 latency,u16 tag)` records, hour-epoch finishing with disorder detection, count/scatter, AVX2 multiselection of three ranks, output in hour order and explicit page cache advice. Its private endpoint table avoids the known unsynchronized shared-tag data race. **Do not reintroduce non-atomic readers of mutable dictionary data.**

Lower-bound accounting: input 238.8 MB / 16.499 ms = 14.48 GB/s effective throughput (all work included, not pure memory throughput); 10.1MB output / 16.499ms = 613MB/s. Six-byte records alone represent 18.6MB logical payload and count/scatter adds another ~12.4MB of latency writes before selection, as well as reads. Observed official M=21.67MB is a **cgroup peak**, not the complete virtual working set: input mmap and output page-cache pages can be discarded, and file reads may be satisfied from cache. A physical DRAM-bandwidth 'hard limit' cannot be inferred from these values without counters. Parsing must inspect the input and read each relevant latency; exact quantiles cannot be obtained from approximate percentile sketches.

Prior A negatives, from developer and official PERF logs: two-pass direct scatter (0.494 vs 0.325s locally on early design), output truncation/writeback pacing, early page zaps, thread-start changes, eight-versus-four streaming schedules, different stream counts, `MAP_SHARED`, O_DIRECT speculation and late-page eviction, all either negative/neutral or unqualified. PR #3's locally favorable CPU estimate did **not** transfer to official K (41.91 vs champion 49.77). Source count is scored; avoid adding 100+ lines for a trivial selector improvement.

## 3. A executable experiments and candidate interpretations

Prototypes: `prototypes/a_select.cpp`, `a_avx_selector.h`, `a_record5.cpp`, `a_output_copy.cpp`. Receipts under `receipts/`. Host: container AMD EPYC 9V74 80-Core Processor, five available CPU cores, g++ 14.2.0, Python 3.13.5; all microkernels built `-O3 -march=native`, and pinned single-CPU tests used `taskset -c 0`. **Different hardware/compiler from official scoring and no whole-program B/D/A/C timing.**

Synthetic Zipf endpoints (1,842) and uniform hour distribution produce 131,049 nonempty groups at 3.1M records; official seed-1 has 126,908. Synthetic output latencies include 0 and uint32 extremes but **not** the organizer's exact endpoint-specific log latency distribution or diurnal weights. At 3.1M, 107,180/131,049 (81.79%) groups have <=16 values but groups <=2 represent only 27,145/3.1M (0.88%) of requests. Thus shortcuts can save many function invocations, but almost no record handling.

**A1 multi-rank selection tournament, nine pinned trials, median isolated time:** full `std::sort` 79,711 µs, repeated `nth_element` 52,875 µs, simple three-value radix selection 54,984 µs, adaptive std sort/nth 58,072 µs, **production-equivalent AVX2 multiselect 25,420 µs**, AVX2 multiselect with n=1/2 direct return 23,059 µs. All methods produced identical checksum for selected p50/95/99 over every synthetic group; the AVX helper copies the actual production bitonic-16 and split-selection machinery. The tiny group bypass is a **9.29% isolated selector gain**, not 9% of 16.499ms, and is sensitive to code layout/branch prediction. Qualification: compare exact original compiler source with only the guarded tiny return and check generated full hashes; measure phase CPU and whole-process K.

**A2 5-byte latency records:** 12 tag bits leave 28 bits for latency in a 40-bit packed record. A sentinel `0x0fffffff` and ordered exact overflow payload recovers full uint32 values; no missing extreme case. On 3.1M generated records, 2,877 overflow values; 6-byte payload 18,600,000B versus five-byte payload 15,500,000B + 11,508B overflow values (~3.09MB saving). Straightforward 5-byte memcpy read/write kernel was ~24–25ms versus 2.5ms for Rec6; an optimized overlapping 8-byte read/write brought it to **4.0–4.55ms**, still a considerable CPU regression. Overlapping 8-byte stores must be prohibited on adjacent records written by distinct workers to avoid data races. A memory-only bound if all 3.1MB reduced official peak M is `(21.67/18.57)^.20≈1.031`, but adding CPU work and source lines may destroy it. **Not a production recommendation** until the finalization/scatter loop is reorganized and full-process memory peaks are proven to fall.

**A3 output bytes:** Production copies 128 endpoint bytes by four AVX2 load/stores then advances output by the actual length. A synthetic 126,908-copy test with ~36.9-byte average names compared unconditional AVX2 versus dynamic `memcpy(len)` versus 1-/2-vector adaptive copying: pinned medians 0.409ms, 1.322ms and 0.869ms. Dynamic copy is 3.2x slower despite fewer actual written bytes. **Do not replace the incumbent vector write with libc memcpy merely to save apparent memory traffic.**

**A4 radical alternatives:** (1) per-group latency linked lists bypass a scatter but require ≥8 bytes per record (u32 value+u32 link, 24.8MB) plus ~0.5MB heads and unpredictable traversals; likely defeats M and cache locality, no implementation measurement. (2) direct histograms per active `(hour,endpoint)` would need, for 126,908 groups x 256 cells x 2 bytes, ~65MB before values; exact 32-bit distribution and p50/p95/p99 require further refinements. (3) rewriting time-ordered epoch finalization to be speculative with no exact fallback violates the frozen no-lateness promise. (4) per-worker pre-aggregation and sorted run merge would add substantial per-group state and merging overhead; no measured advantage over production, which already completes hours as soon as safe. These are cost-based **screening assessments**, not proofs that all such families fail.

**A engineering conclusion:** the source's 16–20ms official wall, 239MB input read and 10MB output mean further dramatic headroom is uncertain. The most actionable measured incremental pilot is n=1/2 exact selector dispatch, but it is expected to contribute much less than 1% complete K unless isolated selector CPU is a large fraction of the box's total. Prefer targeted phase counters and a paired official-equivalent A/B test to another broad rewrite without a distinct cost mechanism. A speculative revisit of 5-byte record storage should only follow a fused, safe packing proposal that removes the observed decoding overhead.

## 4. Track C architecture and prior negatives

C: 3,320,000 rows; ~201.94MB hostile `records.csv` and ~2.18MB `regions.csv`; 200k region lookup rows, 240 countries plus unmatched, 100k-name synthetic pool and 60k-note pool. Headers/BOMs, CRLF/LF and quoted embedded LF, paired escaped quotes, empty names, trailing spaces and negative integer cents are all correctness-critical. The frozen generator guarantees no CR inside quotes and note contents contain no digits (which enables current record split certification), but names/notes must still be compared or length-counted correctly. Country distinctness is **exact per country**, after quote-unescaping, not an approximate cardinality estimate. Unknown lookup keys belong to `_UNMATCHED`.

Winning C joins with a 1,000,000-byte dense region-to-country table, SWAR decimal parsing, a grammar-certified parallel split, 32-row parse/prefetch batches, shared 64-shard name dictionary, 48-byte exact name slots and four atomic 64-bit country-presence words per name; country sums are worker-local. The name pool needs about 100k *48 = 4.8MB of resident slot storage, and its `seen[4]` consumes 3.2MB of those slot bytes. The 64x2048 atomic entry index is another ~0.52MB. Total official memory was only 14.26MB because input and lookup pages are explicitly discarded and worker state is small.

Prior C rejected experiments are not all algorithmic-family failures: direct per-row processing without pending batches regressed 93.764→112.372ms; 64B aligned name slots grew memory; direct atomic slots touched otherwise cold resident pages; increasing name-index shards 64→256 regressed ~1.7%; local per-thread exact-name cache regressed 139.972→153.091ms; speculative record splitting scored disastrous official K=11.387 (230ms); PR-head x86-64-v3 pragma officially regressed. Existing SSE2/AVX2 quote-search experiments yielded modest qualified runner gains, but **they still search for quotes within separate fields**, unlike the proposed fused structural approach. Performance records: `sd-tc/track-c/PERF.md` and `sd-sm/track-c/PERF.md`.

## 5. C: executable, fused quote-aware structural scanning

`prototypes/c_structural.cpp` contains FOUR exact decoding implementations: current-style scalar field scanner; 32-byte AVX2 structural masks with a second quote-count pass; 32-byte structural masks with cumulative quote counts; 64-byte AVX2 structural masks using either 64-bit SWAR quote parity or **PCLMUL quote-prefix parity**. It validates decoded name length, note length, row ID, region ID, exact signed cents and the production-equivalent CRC32C hash of the **raw** encoded name, with field-by-field comparisons between the scalar implementation and 64-byte candidate. Companion `gen_hostile_csv.py` produces reproducible synthetic UTF-8 BOM prefixes, trailing-space names, commas, `""` escapes, quoted multi-line notes, mixed CRLF/LF, empty quoted/unquoted names, and negative amounts.

For a block of 64 bytes, let Q be the bitmask of `"`, C that of `,`, and L that of `\n`. Inclusive quote parity `P_i = XOR_{j≤i} Q_j` identifies whether each byte is inside a quoted field. Since valid doubled quotes are adjacent, `""` toggles parity twice and no comma/LF can lie between those two bytes. With a parity carry between blocks, exact structural delimiters are `(C|L)&~P`. For PCLMUL, low64(`clmul(Q, 0xffff...ffff)`) is precisely the inclusive XOR-prefix. Accumulate popcount(Q) at each structural delimiter to derive decoded quoted-field length as `raw_span−2−(quote_count−2)/2`; count all LF bytes *inside* quoted notes. Only the four true commas and the true record-ending LF delimit a valid record. BOM is skipped only at the record start; CR preceding outside LF is excluded from the final amount. Name CRC32C hashes the raw between-quote bytes, preserving the incumbent dictionary's exact collision policy.

**Correctness:** targeted field-by-field tests passed for 250k, 500k, 750k generated records, and the 500k seed was repeated with name CRC included. No full competition seed was run. Prototype cap 2,048 bytes per record is an artifact of fixed local mask arrays; a production version needs a streaming fallback or larger safe bound. Numeric parsing in the prototype uses scalar loops, not the champion's SWAR numeric routine, so its speed ratios are not directly transferable to the incumbent engine.

**Measured, pinned CPU0, 500k synthetic rows, 27.59MB, nine runs, no name CRC:** scalar 21.4656ms, AVX2 twice-scanned 21.6073ms, AVX2 with cumulative quote counts 18.5916ms, 64-byte PCLMUL 15.2392ms. Plain SIMD without avoiding the second scan did not help.

**Measured including production-equivalent raw-name CRC32C, compiler `-O3 -march=x86-64-v3 -std=c++20`, five pinned runs:** scalar median ~28.344ms; AVX2 cumulative quote count ~24.9456ms; 64-byte PCLMUL ~20.527ms (**~27.6% less parser+raw-hash time**); 64-byte SWAR parity ~21.610ms (**~23.8% less**). Identical checksum on every method and 500,000 row-wise comparisons passed with all semantic fields including CRC32C hash. Run-to-run timings and kernel ratios are **not complete C times or official box results**.

**Compiler/CPU finding:** GCC 14.2 with plain `-march=x86-64-v3` refuses `_mm_clmulepi64_si128` (target mismatch), while per-function `__attribute__((target("pclmul")))` compiles and runs. The scoring image uses GCC 15 `-march=x86-64-v3` with PGO, so retain a SWAR fallback or use safe CPUID dispatch and test the scoring CPU's PCLMUL support. Do **not** globally change C compiler `-march` or disable PGO to obtain a misleading synthetic score.

**Implementation handoff, primary C approach:**
1. Preserve current region array, `SharedNames::first`, 32-row pending batches, exact name collisions and worker-local `Group` aggregation. Replace only the two successive `text_field` / `comma` / `newline` search paths in `parse_range` with one exact record structural scan yielding `id`, name raw slice+decoded length+hash, note decoded length, region id, cents, consumed record length.
2. In each 64-byte load, get `q`, comma and LF movemasks, carry quote parity across loads, harvest structural separators. Keep prefix quote counts at each delimiter for decoded lengths. When the record is too long or a CPU lacks optimized PCLMUL, use the 64-bit XOR prefix (`q^=q<<1;...`) or an exact scalar fallback. Parse BOM only at certified record starts.
3. Keep the current *record boundary splitting* initially. It is already generator-certified and changing it simultaneously obscures performance and exactness. Do not add a whole-file structural tape, which would cost extra passes and memory.
4. Profile separately: parse+mask+numeric, name CRC, name interning/seen atomic, aggregate updates, lookup build, output, and cgroup peak. Use PGO at the exact pinned GCC15 toolchain. Add adversarial masks with quotes straddling bytes 31/32 and 63/64, escaped triple quotes, name empty forms, LF inside quote, true LF after CR, BOM after LF/CRLF, uint32 regions and signed amount extremes within spec.
5. Run first focused 1/4/6 worker sample and one full seed exact comparison, with a *matched* end-to-end timing. Defer full multi-seed/sanitizer/sandbox qualification and board trial to the scheduled developer and Luna.

**Whole-K acceptance:** At unchanged S/M, C must reach T≤60.078ms to displace B. With +50 scored lines, T≤58.536ms. If speedup is confined to a parser stage that is 27.6% faster and S grows 50 lines, that stage must represent **at least 77.3%** of whole-process time (and cgroup M must not rise). With +90 lines, ≥82.8%. These are *model constraints*, not measured phase shares. If the actual share is 50%, full runtime falls ~13.8%, yielding only ~6% K before source penalty and remains below threshold. A genuinely larger overhaul may be necessary; do not present SIMD success as a guaranteed team-score breakthrough.

## 6. C: alternative synchronization and distinctness algorithms

`prototypes/c_distinct.cpp` isolates exact `(country,nameID)` duplicate tracking under preassigned IDs: 100k names, 241 countries, 3.32M records (synthetic uniform name and group choice). Four-worker nine-run pinned-to-five-CPUs medians: shared atomic per-name 4-word `seen` 5,883µs; per-worker private 4-word arrays merged by OR/popcount 8,508µs; sort packed 32-bit `(nameID<<8)|country` with four radix passes 29,699µs; shared *country-major* atomic bitmap 5,391µs. Single-thread pure scalar oracle ~5,798µs. All methods returned the same 3,101,423 distinct pairs. These are *only presence-update and merge* costs; no string hash/interner or CSV parser. Country-major layout needs 241*ceil(100k/64)*8=3,013,464B versus 100k*4*8=3.2MB name-major. A small isolated gain does not justify a large source rewrite unless replicated with the real dictionary and NUMA/SMT context.

Serious unqualified contenders:

- **C-global-country bitmap:** change `Slot::seen[4]` into one global `atomic<uint64_t>[241][ceil(maxNames/64)]` indexed by exact canonical name ID, letting `first(name, country)` use `fetch_or(1<<(id&63))`; the name dictionary still resolves exact ID, preserves collision checks and can interleave inserts. Memory may decrease modestly for bitset itself, but moving it out of Slot48 may require name slot redesign and extra cache misses. Microkernel gained only ~8%, memory may increase if leaving the old seen words unused; consider only after primary fused parser.
- **Per-worker private bitmaps:** avoids atomic RMW, but costs `threads*3.2MB`, plus multi-megabyte OR merge. The measured 4-thread 8.5ms versus 5.9ms for shared atomics rejects this representation in isolation. A memory-saving sparse worker design could be revisited only if a new working-set model demonstrates advantage.
- **Deferred packed sort:** 3.32M 32-bit keys are 13.28MB plus another 13.28MB scratch; four radix passes read+write ~106MB and require a separate exact name dictionary phase. Measured ~29.7ms versus 5.9ms for shared atomic presence updates: strongly unfavorable as a drop-in replacement. An integrated name-ID assignment plus partitioned streaming sort would be a *different algorithm* and was not tested.
- **Country-local exact hash sets:** would store up to approximately 3.1M distinct `(country,name)` entries (vs ~100k distinct names), likely tens of MB even with packed keys; memory penalty makes the full K threshold stricter. Not benchmarked as a complete engine.
- **Owner-computes keyed sharding:** parse workers route compact `(nameHash,rawName,country)` events to shard owners in batches, avoiding shared atomic dictionary access. Requires synchronization/queues and reference lifetime management; event tape at 16 bytes/record is 53.1MB before buffers, so candidate must be streaming, not materialize a whole tape. High effort; no credible win demonstrated yet. Keep as a second-phase architecture if fused parser fails after measured integration.

## 7. C whole-work cost map and opportunity limits

The earlier PGO/pragma problem demonstrates that compile and training context matter as much as unpinned kernel rates. Any C test must use the actual Docker build script and its training seed without leaking official input artifacts. Costs plausibly include roughly 200MB input scan, dense region lookup, 3.32M CRC32 name hashes, ~3.32M random probes into a 100k-name dictionary, ~3.32M atomic presence updates, 3.32M country reductions and minimal final 240-group output. **No phase-level C timing on the official scoring host was obtained in this research; percentages not measured must be treated as hypotheses.**

Input ~202MB / 74.402ms = 2.72 GB/s implied total throughput, considerably below A's effective file-throughput rate, but this alone does not prove an input memory bandwidth bottleneck: CSV structural parsing and random name-index cache misses are substantial. The fused scanner avoids the current two quoted-field scans, but name CRC and global name dictionary remain required. A successful reduction in structural parsing time does not eliminate name-table work.

Potential wins must satisfy source and memory axes. If C's source grows 90 scored lines and M unchanged, with parser improvement 27.58%, estimated C K would be ~22.78 if the parser+hash share is 80% (still below B), or ~23.14 if the share is 90% (still just below B). It needs ≥82.8% phase share at +90 lines to cross, and even higher if M increases. A ~10% K gain alone does not suffice (20.893*1.1=22.982). A 20% K gain would yield C K≈25.07, which would replace B and improve overall geometric mean about 2.5%; the exact gain depends on B/D concurrent progress. A 30% K gain would put C≈27.16 and increase team overall about 5.3% at this snapshot.
